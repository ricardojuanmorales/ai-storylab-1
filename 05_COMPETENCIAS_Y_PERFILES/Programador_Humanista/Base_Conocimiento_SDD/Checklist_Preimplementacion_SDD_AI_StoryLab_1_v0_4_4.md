## 1. Propósito

Este checklist ayuda al Programador Humanista a verificar si una propuesta está lista para avanzar dentro del marco SDD.

En v0.4.4, “lista para avanzar” significa lista para revisión documental, no lista para implementar.

---

## 2. Checklist de existencia documental

```text
[ ] Existe una spec redactada.
[ ] La spec usa la Plantilla de Spec Segura vigente.
[ ] La spec tiene ID, título, versión, estado y responsable.
[ ] La spec declara ruta propuesta.
[ ] La spec identifica documentos relacionados.
[ ] La spec declara alcance y no alcance.
[ ] La spec declara explícitamente que no autoriza implementación funcional.
```

---

## 3. Checklist de propósito humano

```text
[ ] La spec explica qué necesidad humana, educativa, creativa o investigativa atiende.
[ ] Identifica a quién sirve.
[ ] Explica qué experiencia protege o habilita.
[ ] Evita formular el propósito solo como tarea técnica.
[ ] Incluye frase “sin autorizar...” cuando corresponda.
```

---

## 4. Checklist de subjetividades y perfiles

```text
[ ] Identifica subjetividades afectadas.
[ ] Identifica perfiles operacionales afectados.
[ ] Reconoce si hay estudiante de escuela superior.
[ ] Reconoce si hay docente o investigador.
[ ] Reconoce si hay evidencia educativa, evaluación o publicación.
[ ] Aumenta nivel de cuidado si hay menores o evidencia sensible.
```

---

## 5. Checklist local-first

```text
[ ] Declara qué permanece local.
[ ] Declara qué no se guarda.
[ ] Declara qué puede exportarse.
[ ] Declara qué requiere consentimiento.
[ ] Declara qué requiere anonimización.
[ ] Declara qué nunca se sube automáticamente.
[ ] Declara qué requeriría spec futura.
[ ] No introduce backend.
[ ] No introduce cloud.
[ ] No introduce APIs externas.
[ ] No introduce autenticación.
[ ] No introduce analíticas.
[ ] No introduce base de datos remota.
[ ] No introduce subida automática de archivos.
```

---

## 6. Checklist de datos

```text
[ ] Clasifica todos los datos involucrados.
[ ] Justifica cada dato.
[ ] Elimina datos innecesarios.
[ ] Distingue datos ficticios, sintéticos, anonimizados, personales, educativos y sensibles.
[ ] Identifica metadatos.
[ ] Identifica evidencias creativas.
[ ] Identifica reflexiones personales.
[ ] Identifica si hay datos de menores.
[ ] Mantiene principio de minimización.
[ ] Bloquea manejo de datos reales si no existe política formal.
```

---

## 7. Checklist de evidencias y portafolios

```text
[ ] Identifica si la spec crea evidencia.
[ ] Identifica si organiza evidencia.
[ ] Identifica si transforma evidencia.
[ ] Identifica si interpreta evidencia.
[ ] Identifica si exporta evidencia.
[ ] Trata evidencia como objeto de cuidado, no como archivo neutro.
[ ] Permite revisar.
[ ] Permite editar.
[ ] Permite retirar.
[ ] Permite no compartir.
[ ] Prohíbe publicación automática.
[ ] Prohíbe evaluación automática como juicio final.
```

---

## 8. Checklist de consentimiento

```text
[ ] Determina si se requiere consentimiento.
[ ] Explica qué ocurrirá.
[ ] Explica qué datos se usarán.
[ ] Explica para qué se usarán.
[ ] Explica quién tendrá acceso.
[ ] Explica riesgos.
[ ] Explica alternativas.
[ ] Explica cómo negarse.
[ ] Explica cómo retirar autorización cuando aplique.
[ ] Usa consentimiento reforzado si hay menores, datos reales, publicación, exportación o IA externa.
```

---

## 9. Checklist de IA

```text
[ ] Declara si no aplica IA.
[ ] Si imagina IA futura, la mantiene conceptual y no implementada.
[ ] Si considera IA externa, exige spec específica.
[ ] Si considera IA externa, exige consentimiento explícito.
[ ] Si considera IA externa, usa solo datos ficticios, sintéticos o anonimizados.
[ ] Si considera IA externa, exige threat model.
[ ] Si considera IA externa, exige revisión humana.
[ ] Prohíbe IA como juez final.
[ ] Prohíbe IA como sustituto del docente.
[ ] Prohíbe IA como autoridad sobre valor creativo.
[ ] Prohíbe IA como mecanismo de vigilancia.
```

---

## 10. Checklist de experiencia creativa no rígida

```text
[ ] Evita exceso de campos obligatorios.
[ ] Evita flujo único obligatorio.
[ ] Evita que el portafolio sea archivo muerto.
[ ] Evita reflexión como trámite.
[ ] Evita experiencia centrada en cumplimiento.
[ ] Permite exploración.
[ ] Permite pausa.
[ ] Permite revisión.
[ ] Permite error.
[ ] Permite recombinación.
[ ] Permite decisiones del usuario.
```

---

## 11. Checklist de threat model

```text
[ ] Identifica activos a proteger.
[ ] Identifica actores o fuentes de riesgo.
[ ] Identifica amenazas previsibles.
[ ] Identifica mitigaciones.
[ ] Identifica riesgos residuales.
[ ] Determina si el threat model preliminar basta.
[ ] Determina si se requiere threat model específico.
[ ] Bloquea avance si hay amenazas críticas sin mitigación.
```

---

## 12. Checklist de revisión humana

```text
[ ] Identifica si la revisión humana es obligatoria.
[ ] Registra revisor/a.
[ ] Registra perfil del revisor/a.
[ ] Registra fecha.
[ ] Registra resultado.
[ ] Registra justificación.
[ ] Permite aprobar.
[ ] Permite condicionar.
[ ] Permite diferir.
[ ] Permite bloquear.
```

---

## 13. Checklist de trazabilidad

```text
[ ] Vincula con Constitución SDD.
[ ] Vincula con Plantilla de Spec Segura.
[ ] Actualiza bitácora de sesión.
[ ] Actualiza transferencia simétrica.
[ ] Actualiza registro de deuda.
[ ] Identifica deuda creada.
[ ] Identifica deuda pagada.
[ ] Identifica documentos que deben actualizarse.
```

---

## 14. Criterios de bloqueo automático documental

Bloquear, diferir o escalar si aparece cualquiera de estos elementos:

```text
[ ] Backend.
[ ] Cloud.
[ ] APIs externas.
[ ] Autenticación.
[ ] Analíticas.
[ ] Base de datos remota.
[ ] Subida automática de archivos.
[ ] Uso de IA externa por defecto.
[ ] Manejo de datos reales.
[ ] Evaluación automática como juez final.
[ ] Publicación automática.
[ ] Implementación funcional.
[ ] Menores de edad sin consentimiento reforzado.
[ ] Evidencia sensible sin revisión humana.
[ ] Riesgos sin mitigación.
```

---

## 15. Dictamen

Este checklist no decide por sí solo. Ayuda a que la revisión humana tenga un mapa claro.

Si el checklist produce demasiadas alertas, la spec no debe avanzar. Si produce claridad, la spec puede pasar a decisión documentada.
